## Правила периода и классификации

- Основная дата продажи: дата положительного Finance-начисления Ozon.
- Дата заказа и дата доставки по Posting API сохраняются отдельными полями.
- Если положительное начисление отсутствует для подтверждённой продажи СНГ, используется дата валидированного отчёта СНГ.
- Если Finance-дата недоступна и нет отчёта СНГ, допускается резервная дата доставки с явным признаком источника; такие строки считаются предметом проверки.
- Возврат не создаёт отрицательную продажу в дате возврата. Он уменьшает количество и выручку исходной продажи, а расходы Finance остаются на своих датах начисления.
- Компенсации с номером заказа/отправления входят в юнит-экономику связанного заказа отдельным доходом, но не в выручку продаж и не в количество.
- Подписки и другие начисления без связи с заказом не входят в юнит-экономику и учитываются только в итоге периода.

## Обязательные автоматические проверки перед публикацией

1. Нет дублей по ключу отправление + SKU + дата учёта продажи.
2. Выручка строки равна net-количеству × цене за единицу.
3. Возвращённое количество не превышает проданное.
4. Все возвраты Returns API для найденных продаж отражены в net-количестве.
5. Положительная Finance-дата определяет отчётный период продажи, если она доступна.
6. Компенсации с известным заказом/отправлением связаны только с его SKU; начисления без такой связи не распределены.
7. Все подтверждённые отправления СНГ либо присутствуют в основном API-слое, либо добавлены ровно один раз из валидированного отчёта.
8. Полная сумма Finance API сверяется с прямыми расходами, общими начислениями и компенсациями без необъяснённого остатка.

## Открытые вопросы из файла сверки

- Отправление `52304939-0332-1`: требуется повторная проверка в ЛК и сырых API-источниках.
- Остальные строки с разницей только в дате должны автоматически исчезнуть из расхождений после перехода на Finance-дату продажи.
- После следующей синхронизации необходимо пересчитать весь август и заново сравнить каждое отправление с ручной таблицей.
